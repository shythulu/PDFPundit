How it works

PDFPundit ignores the damaged file's own index. It rebuilds the document from whatever objects survive in the bytes, then grades everything it wrote.

Design, not code. This page describes the planned engine. The full design is in the technical design.

The method

The method starts from REPDF, a peer-reviewed repair method from DFRWS 2026. REPDF repairs PDFs with an external font database and by rebuilding the links between surviving objects. Its code and corpus are public: 1,000 damaged PDFs in 6 languages.

PDFPundit reimplements that method in Rust. The research aims to go past it. See the research guide.

Repair steps

  1. Carve. Scan the raw bytes for every N G obj … endobj. Expand compressed object streams too, because PDF 1.5 and later hide most objects inside them.
  2. Decode. Inflate each stream and sort it into content, image or font.
  3. Link. Rebuild the object graph from /Root to /Pages to each /Page.
  4. Restore fonts. Re-link lost fonts, or substitute from the bundled font database. Rebuild /ToUnicode so text stays searchable.
  5. Write. Emit a new file with a fresh cross-reference table and trailer.
  6. Check. Diagnose the output again to confirm each problem is gone.

The engine runs these as background jobs. It streams progress and findings as events, so any interface can sit on top of it.

Damage classes

REPDF defines ten damage classes. Each one becomes a detector and a repair pass.

IDDamageRepair approach
C1Header overwrittenRewrite a valid %PDF-x.y header
C2Cross-reference table removedCarve all objects, rebuild the table
C3Trailer removedFind /Root and /Info, rebuild the trailer
C4Page tree brokenCollect /Page objects, rebuild /Pages
C5Object tags strippedFind object boundaries by structure, renumber
C6Font mapping lostRe-link pages to their carved fonts
C7Font program deletedSubstitute from the font database
C8Font program and /ToUnicode deletedSubstitute the font, rebuild the Unicode map
C9Compressed stream damagedSalvage what decodes, then verify it
C10File truncatedAssemble a document from what survives

The research has found 23 more damage classes beyond these ten. Examples are holes in the middle of a file, broken incremental updates, transfer mangling and producer bugs.

Provenance grades

Every element of a repaired file gets exactly one grade. A reader can then see which content is original and which was synthesized.

#GradeExample
1VerbatimBytes copied unchanged
2Partially decodedStream output shown to be independent of the damage
3Corrected and verifiedThe only candidate that passes a checksum and an independent check
4Structurally inferredPage order, renumbered objects, chosen revision
5Non-content synthesisNew xref, trailer, /Length, header
6Content synthesisSubstituted fonts, generated /ToUnicode, default page size

Why grades 2 and 3 are strict

The research showed that two common shortcuts produce wrong output.

  • Decoding a damaged stream until it errors gives wrong bytes in 95% of the damaged streams in REPDF's C9 files. So a decoded prefix isn't grade 2 by default.
  • A checksum match doesn't make a correction unique. So grade 3 also needs an independent check, such as replaying the encoder.

When several candidates pass, the differing bytes are marked unknown. The engine doesn't guess.

Two kinds of failure

FailureMeaning
FabricationOutput content that wasn't in the original. A wrong glyph mapping, page order or revision.
OmissionContent that survives in the damaged bytes but the repair drops

Both are measured. Omission is measured against an upper bound computed from the damaged file itself.

Hostile files

Accidental damage is what PDFPundit repairs. Hostile input is something it detects. That covers decompression bombs, exploits and deliberate tampering, such as shadow attacks through incremental updates.

Signs of tampering are reported, never repaired away.

Design rules

  • Pure Rust. No compiled C in the shipped binary.
  • lopdf is the only PDF writer.
  • The original file is never changed.
  • Dependencies are MIT or Apache licensed.
  • The engine knows nothing about the interface. The terminal UI is designed separately.
