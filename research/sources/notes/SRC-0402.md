# SRC-0402: CPR, REPDF's sibling at DFRWS EU 2026

**Why it matters.** This is the closest competitor to PDFPundit's font path, and it appeared in the
same venue and year as REPDF (SRC-0001). It replaces REPDF's dictionary scoring with **LLM
validation** (a local Llama 3.1:8B, CLM-0401). It is the first PDF-repair paper to put a learned
model in the recovery loop, so it is the first test case for charter §3(c).

Scope overlap: CPR is also forensics literature. Check for a duplicate record from `scoping-forensics` at merge.

## Method
1. **Producer analysis (Table 1).** Six generation methods collapse to four fingerprints (macOS Document Editor, MS Save as,
   MS Print to PDF, Adobe Acrobat). They are identified by object-number order, content-stream prologue and
   font-tag scope (global or per page).
   - **Key finding:** macOS assigns CIDs *sequentially from 21 by first appearance* (CLM-0411). Codes then carry no GlyphID
     identity, so no font DB can decode them.
2. **FontDB.** Common TTF/OTF/TTC fonts are converted with fontTools. The glyphorder and name tables are read, and glyph
   names are mapped to Unicode through the Adobe Glyph List (CLM-0400). It is keyed by PostScript name (nameID 6).
3. **Preprocess.** Objects are carved with an `obj`/`endobj` regex. A corrupt object is detected by an offset/length
   inconsistency and split at the next valid header. `endstream` is appended so inflate can still run.
4. **Parsing.** A FontCMap is built: global or per page (`pidx`). Surviving ToUnicode/FontFile CMaps are stored as
   auxiliary `Random#` entries. The Content stream is split into Text, XObject and Path objects. Path-drawn text is
   rendered to PNG rather than recognised.
5. **Mapping.** Candidate CMaps are tried in turn, and each decoding is judged O/X by the LLM. After K=5 successes a
   font is "confirmed". If nothing is confirmed, CPR falls back to **brute force over the whole FontDB, keeping only
   LLM-accepted mappings**.

## Evaluation
- **Data.** 22 ground-truth sets: 10 fonts, English/French/Korean, 6 producers, 3–5 pages each (CLM-0408).
  655 corrupted files, made by deleting 8 content-related object types (CLM-0410). The FontDB (40 fonts) covered
  **every** test font (CLM-0407), so the test is closed-world.
- **Metrics.**
  - Recovery success counts *any* partial recovery (CLM-0409). This is lenient; see GAP-008.
  - CER (Levenshtein) and word P/R/F1 on successful files.
- **Baselines.** PDF24, pdf4me, pdfonline, iLovePDF (all web tools). No open-source engines, the same weakness as REPDF (GAP-009).
- **Results.**
  - Mean success 0.924.
  - Complete CMap loss: **33.3% success, CER 0.048** (CLM-0402), blamed on LLM misclassification (CLM-0403).
  - macOS with no CMap: impossible (CLM-0404).

## Limitations and future work (verified)
- Producer-internal CIDs are unrecoverable without a CMap (CLM-0404).
- LLM false positives and negatives on single-character or low-context CIDs (CLM-0405).
- Future work: fine-tune the LLM verifier (CLM-0406), and more producers.

## Our reading (critique, not evidence: CLM-0445)
- **Fabrication.** The validator judges *naturalness*, the same prior that makes VLMs rewrite text (SRC-0422). Plausible but wrong
  mappings are accepted by design. No fabrication rate is reported (GAP-201).
- **Determinism.** Decoding settings, seed and model checksum are not reported, so charter §3(c) cannot be checked.
  Llama 3.1 is distributed under Meta's community licence, not an OSI licence; the tooling stage should verify this.
- **Confidence.** Verdicts are binary; there is no per-mapping confidence for provenance grades (GAP-204).
- **Glyph evidence unused.** Embedded glyph outlines are not used for font identification, even when FontFile survives.
  Font identity comes only from names and brute force (GAP-003, GAP-200).
- **Scripts.** No Arabic or Indic script was tested, so REPDF's weakest case (GAP-004) is untested here too.
- **Replication.** The code, dataset and FontDB are public (CLM-0412) but **CC BY-NC**: usable as a research baseline only,
  never in the product.
