# SRC-0204 — Cross-reader inconsistencies on Govdocs1

**Why it matters:** the only large, real-world measurement we found of how often *intact* PDFs are
rendered differently by different engines. It sets the floor for any cross-engine agreement metric
(charter §3(a) robustness, GAP-012) and states file repair as future work.

## Method
- Manual study: one-percent random sample (2,313 files) of Govdocs1, first page, 8 graphical readers
  on Linux (CLM-0241); majority vote defines "correct" (CLM-0242).
- Automated pipeline over 230K files: crash/error-message capture, per-reader clustering by error
  messages, CW-SSIM image comparison of cluster representatives, delta debugging to localize objects.

## Findings (verified quotes)
- 13.5% of files inconsistent in at least one reader (CLM-0240), probably more over all pages (CLM-0243).
- Same error messages can still render differently because recovery strategies differ (CLM-0244).
- Automated detector precision/recall/F1 = 33%/60%/43% (CLM-0249).
- Reader developers patch to tolerate malformed files (CLM-0248). None of the sample was PDF/A or
  PDF/X (CLM-0250). Flattening can add inconsistencies (CLM-0251).

## Limitations and future work (verified)
- Common-mode failures (all readers wrong the same way) are invisible (CLM-0245).
- Future work: automatically fix the PDF files (CLM-0246), hard because of xref offsets and object
  numbering (CLM-0247). No follow-up doing this was found among the 13 OpenCitations citers.

## Our reading (not evidence)
- Majority vote is the only oracle when originals are unknown. That is precisely the charter's
  "found files" setting, and it cannot see common-mode errors (CLM-0290).
- A repaired file should be compared against the *damaged* file's own cross-engine disagreement,
  not against zero: 13.5% of undamaged files already disagree.
- Their bug database (srg.doc.ic.ac.uk/projects/pdf-errors) is a candidate source of real
  malformed files with reader-bug labels; not checked.
