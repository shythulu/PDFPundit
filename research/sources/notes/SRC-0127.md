# SRC-0127: Force Open (black-box repair by hijacking the viewer)

**Why it matters:**
- It is one of very few forensic-venue repair papers that evaluates on **PDF**.
- It states repair as a two-objective problem: keep the original's information (omission) and
  add none of its own (fabrication) (CLM-0111).
- It gives the only file-level evidence found that two repair tools are **complementary** (GAP-053).

## Method
1. **Training.** Binary instrumentation (Intel Pin) records, for many valid files, the
   conditional branches whose outcome is the same for every valid file.
2. **Force open.** When a corrupted file is opened, those branches are forced (execution
   hijacking). The file itself is not modified (CLM-0112).

No format knowledge or viewer source code is needed. The "repair" is the viewer's output
(pdftotext text for PDF), not a repaired file.

## Evaluation
- **Damage:** synthetic. n ∈ {1, 2, 4, 8, 16} random bytes overwrite a random position, and the
  copy is kept only if the viewer then fails (CLM-0116).
- **PDF setup:** 158 text-based PDFs for training. The viewer is pdftotext, the baseline pdftk,
  and the metric the Levenshtein distance to pdftotext's output on the original.
- **PDF results:**
  - every file Force Open opened gave identical text: all-or-nothing (CLM-0113);
  - pdftk wins on larger corruptions;
  - the overlap is small, so the union repairs 31.30% more PDFs (CLM-0114, CLM-0115).
- Code and data: github.com/fldpi/forceopen (not fetched).

## Limitations (stated)
- It can't fix data-dependent corruption that isn't an if-then-else decision (CLM-0117).
- Large, block-sized corruptions are out of reach.
- Bypassing integrity checks is exploitable, so the viewer must be sandboxed (CLM-0118). This is
  relevant to the hostile-input side of GAP-015.

## Our reading
- **Not a repair in the charter's sense.** It emits no conforming PDF and no provenance. Its
  output could, though, serve as an *oracle signal*: what a tolerant consumer can extract when
  its checks are bypassed.
- **Evidence for tool portfolios** (research question 5, GAP-053). The complementarity result is
  from 2017, one tool pair and synthetic damage; the charter §3(b) baseline protocol should
  report overlap, not just per-tool rates.
- **Lead:** it cites Docovery (Kuchta et al., ASE 2014), symbolic-execution document recovery
  that needs the viewer's source. That belongs to the program-repair community; not screened here.
