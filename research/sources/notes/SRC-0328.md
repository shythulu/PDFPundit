# SRC-0328: E-APR (repair-strategy selection)

**Why it matters:** the closest published answer to RQ5 (gentle-gosling s2): how to choose a repair
technique per instance from diagnostic features. It applies Rice's algorithm-selection framework
and instance space analysis to 11 program-repair tools.

## Method
- Data: 2,141 bugs from 130 projects, 23,551 repair attempts (CLM-0327), from the RepairThemAll
  experiment. Label = "a plausible patch was found".
- About 146 program and bug features; select those that correlate with success; project instances to
  2-D and draw each tool's "footprint" (region of strength).
- Multi-label classifiers (SVM, random forest, decision tree, MLP) predict which tools will succeed.

## Results
- Effectiveness is instance-dependent; no technique is best everywhere (CLM-0328).
- Random forest: 88% precision, 81% recall, 84% F1 for selecting a suitable tool (CLM-0329).
- Selection overhead is seconds (static features) plus milliseconds (prediction).
- Current infrastructures run tools in a fixed order or leave the choice to the user (CLM-0332).

## Limitations (verified quotes)
- Trained on plausible, not correct, repairs (CLM-0330). Correct-patch data covered only 20 bugs,
  too few to learn from (CLM-0331).
- No abstention: the selector always recommends something. There is no confidence threshold or
  escalation path.

## Transfer to PDFPundit (our inference)
- Map: tool = repair toolpath (Resave, TemplateAssemble, stream correction, resync, ...); features =
  diagnosis outputs (C-class signals, blocks per stream, checksum status, candidate counts,
  font-inference confidence); label = **fidelity against the known original**, never "opens in a viewer"
  (that is PDF's "plausible patch", and it hides fabrication).
- Evaluate as algorithm-selection work does: against the single best toolpath and the per-file
